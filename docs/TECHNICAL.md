# How the patch works, in detail

> [!WARNING]
> **This file was generated by an AI (Codebuff) and probably contains mistakes.**
> The offsets, section behaviour and checksum values were checked against the one
> console it was written for; the surrounding explanation was not reviewed by
> anyone, and generalisations beyond that build may be wrong. Measure before you
> trust it.

All of this was measured on a real console: Playden for PS4 `ps4-v0.2.0`,
Oblivion GOTY from Steam (app `22330`), OBSE 0021, NorthernUI. If you are
porting this to another game or another Playden build, this is the part worth
reading.

## 1. What Playden does to the exe

The Steam download of Oblivion is 7,898,624 bytes with an entry point at
`0x7AF2ED`. When Playden prepares the game it rewrites `Oblivion.exe` — the
"de-stub" — producing a 7,549,440-byte file with the entry point at `0x58787C`.

Measured effect of that rewrite:

| | before | after |
|---|---|---|
| file size | 7,898,624 | 7,549,440 |
| entry point | `0x7AF2ED` | `0x58787C` |
| `.bind` section (VA `0x7AF000`, size `0x56000`) | present | removed |
| every other section's RVA and bytes | — | **identical** |
| PE checksum | set | zeroed |
| Adler32 as OBSE computes it | `0xA2408F04` | something not in OBSE's table |

Because only `.bind` disappears and the remaining sections keep their RVAs,
OBSE's hardcoded addresses still line up. The rewrite is *not* what breaks OBSE
by itself — the checksum is.

## 2. OBSE's version check

OBSE does not look at version resources. `obse/obse.cpp` computes:

```c
// clear the LARGE_ADDRESS_AWARE bit, then Adler32 the whole file
data[0x13E] &= ~0x20;
adler = adler32(1, data, size);
```

and looks `adler` up in a table of supported builds:

| crc | build | dll |
|---|---|---|
| `0x7934C86C` | retail 1.2.0.416, no steam flag | `obse_1_2_416.dll` |
| `0xA2408F04` | retail 1.2.0.416, steam flag | `obse_1_2_416.dll` |

A match sets the internal "game version" and the desktop/steam path; anything
else produces *"You have an unknown version of Oblivion"* and the process exits.
This is **Adler32, not CRC32** — "fixing the CRC" does nothing, and the PE
checksum is irrelevant to OBSE.

`tools/obse_crc.py` reproduces this exactly; `tools/check_crc.py` prints it for
any exe.

## 3. Why `obse_loader.exe` cannot work here

The loader (`main.cpp`) starts Oblivion with `CreateProcessW` using
`CREATE_SUSPENDED`, writes the OBSE DLL path into the target's memory, queues an
`LoadLibraryA` APC, and resumes the thread. The Playden/Orbis-Win exec chain
refuses to create a suspended process for a launcher-spawned game and returns
error **50** (`ERROR_NOT_SUPPORTED`), which the loader reports as:

```
Assertion failed in main.cpp (129): Launching Oblivion failed (code = 00000032 (50))
```

Upstream Playden hit the same failure for Fallout 3, Morrowind and FF7 —
[issue #361][issue-361], closed once the exec chain learned to honour suspended
creation. The PS4 port used for this work predates that, and later PS4 builds may
still refuse it.

Rather than depend on that, the patch removes the launcher from the chain.

## 4. The self-loading stub

`tools/mk_obse_exe.py` appends a `.obse` section and repoints
`AddressOfEntryPoint` at it:

```
60                pushad
68 <dll name VA>  push "obse_1_2_416.dll"
ff 15 <IAT slot>  call dword ptr [LoadLibraryA]
61                popad
e9 <rel32>        jmp <original entry point>
90 ...            padding to 16 bytes
"obse_1_2_416.dll\0"
```

`DllMain` of OBSE runs inside the game's own process during `LoadLibraryA`, so
its hooks are installed before any game code executes. `pushad`/`popad` keep the
original entry state intact, and the jump keeps the original entry point and its
`__security_init_cookie`/CRT startup order.

Details that matter:

- **Section header space.** The header write happens at
  `last_section_header_offset + 40`, guarded by `SizeOfHeaders`. If a future exe
  fills the header area to the boundary, this must become a header rebuild.
- **Alignment.** `VirtualAddress` is aligned to `SectionAlignment` (0x1000),
  `SizeOfRawData` to `FileAlignment` (0x200); the file must physically end at the
  last section's raw end, which is asserted.
- **The IAT slot.** `pefile`'s `ImportData.address` returns a bogus value on the
  de-stubbed exe (`0x00E28118`, outside the image), so the patcher computes
  `ImageBase + FirstThunk + 4 * index` instead. For this build that yields RVA
  `0x628118` → VA `0x700CFC`, whose thunk points at the hint/name entry for
  `LoadLibraryA` (hint 594). Verify that before trusting the section layout on a
  different exe.
- **Character set.** `LoadLibraryA` (not `W`) keeps the stub ASCII-only.
- **Section flags.** `0x60000020` = `CODE | EXECUTE | READ`.

The size cost is one section: 7,549,440 → 7,550,484 bytes.

## 5. Forcing the Adler32

Appending the stub changes the hash, so the patcher has to put the file back on a
value OBSE accepts. Adler32 is linear in its input bytes, which makes that a
small linear system rather than a search.

For a file of length `L` with bytes `x_i`:

```
a = 1 + Σ x_i                    (mod 65521)
b = L + Σ (L - i) x_i            (mod 65521)
```

Appending a `k`-byte overlay `y` shifts those by `Σ y_j` and
`Σ (k - j) y_j` plus a `k * a` term. The solver:

1. Runs Adler32 over the patched file to get `(a0, b0)`.
2. Chooses a total `T = Σ y` that makes the low word land on the target: since
   `a` after the overlay is `a0 + T (mod P)`, `T` is fixed modulo `P`. A
   pre-pad of `255`s brings the running `a` up to the target low word.
3. Solves the high word with four free bytes `y0..y3` using a vectorised search
   over the `(y0, y1)` grid (numpy), deriving `y2, y3` in closed form, over
   plausible overlay lengths.
4. Re-runs `obse_adler()` on the finished file and only writes it if the value
   matches — the solver is never trusted blindly.

Target `0x7934C86C` is preferred over the steam value because it takes OBSE's
normal desktop path, which is the one that works under this runtime.

`--target` lets you point the patcher at another table entry if OBSE changes.

## 6. Surviving Playden's repair

`/data/PLDN10001/games/22330/.playden-tree` is a tab-separated manifest, one line
per file:

```
<sha1>\t<size>\t<name>
```

Playden hashes the folder before launching and restores anything that does not
match. That is why a hand-patched exe reverts on the next Play.

`install.py` therefore:

1. uploads the patched bytes as **both** `Oblivion.exe` and
   `OblivionLauncher.exe` (the recipe may start either),
2. downloads `.playden-tree`, rewrites the two matching rows to the new SHA-1 and
   size, and uploads it back,
3. reads both files back and compares SHA-1s.

If `.playden-tree` is missing, the installer says so and continues — Playden
will then hash the files itself.

## 7. Where OBSE looks for plugins

OBSE 21.4 logs:

```
plugin directory = Z:\data\PLDN10001\games\22330\Data\OBSE\Plugins\
```

That is the only directory it scans. Mod archives commonly ship
`OBSE\Plugins\` next to the exe — putting files there does nothing. The installer
creates `Data\OBSE\Plugins` and copies `NorthernUI.*` into it.

`Data\OBSE\obse.ini` is written only if it does not already exist, with
`bCreateCrashDump=1` so a bad plugin leaves evidence.

## 8. FTP specifics

GoldHEN's server is plain FTP, no TLS, anonymous login, port 2121, root `/`.
Notable behaviour on this build:

- `STOR` overwrites existing files fine.
- `MKD` works under `Data/OBSE` but fails for some paths; the installer ignores
  `MKD` errors and relies on directories that already exist, so create
  `Data/OBSE` by installing OBSE first (which the installer does).
- Listing `/data/PLDN10001` may be denied (`drwx--x--x`), so the game folder is
  probed by known paths rather than by walking the tree.
- `SIZE` on a missing file raises; the installer treats that as "not there yet".

## 9. Reproducing the build

```bash
python tools/mk_obse_exe.py work/Oblivion.console.exe out.exe --target 0x7934C86C
python tools/check_crc.py out.exe
```

For the console's exe the result is deterministic: 7,550,484 bytes,
`sha1 7475859baf5bb7bfa50c549f66e1bbe7943598c0`.
